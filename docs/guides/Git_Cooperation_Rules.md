### 🤝 核心配合方式

**開發流程簡述：** 本專案採用 **Monorepo** 架構，前端與後端程式碼分別存放於 `frontend/` 與 `backend/` 目錄。所有同仁統一在 `develop` 分支進行任務開發（`feature`）。**開發與測試必須在 Docker Compose 環境中進行**，以確保所有人的開發結果（如資料庫結構、API 路徑）完全一致。

---

### 🌿 專案分支管理與工作流規範

為了確保代碼品質與本地驗證的嚴謹性，採用以下模式：

#### 1. `main` 分支：正式穩定版本 (Stable Release)

- **定位**：存放已完成所有功能測試、最穩定的程式碼。
- **操作限制**：**嚴禁直接 Commit。** 僅接受來自 `develop` 的合併請求 (Pull Request)。

#### 2. `develop` 分支：開發整合中心 (Integration)

- **定位**：主要的整合分支，匯集所有已完成開發的功能。
- **操作限制**：開發時不應直接在此分支寫 code，必須從此開出 `feature/` 分支進行開發。

#### 3. `feature/` 分支：任務導向開發 (Task-Oriented)

- **定義**：一個分支代表一個獨立的「任務」或「功能」。
- **純前端任務**：僅修改 `frontend/` 下的 Vue 組件或樣式。
- **純後端任務**：僅修改 `backend/` 下的 API、模型或業務邏輯。
- **全端任務**：在同一個分支內完成 `backend/` 的 API 開發與 `frontend/` 的介面串接。

- **使用流程**：從 `develop` 切出 -> 在本地 Docker 環境驗證 -> 推送到 GitHub 並發起針對 `develop` 的 PR。

#### 4. `hotfix/` 分支：緊急修復

- **來源**：從 `main` 分支開出。修復後須同時合併回 `main` 與 `develop`。

### 💡 備忘錄

- **開工前**：

1. 切換至 `develop` 並執行 `git pull`。
2. **執行 `docker-compose up --build**`：確保本地的 Docker 容器環境、資料庫結構（SQLModel tables）與前後端套件依賴是最新的。

- **收工前**：將進度 `commit` 並 `push` 到自己的 `feature/` 分支。
- **發 PR 時**：請詳細說明改動範圍（前端/後端/資料庫）及測試結果。

---

### 📝 Commit 提交規範

請遵守 **「前綴 + 簡短描述」** 的格式，簡短描述具體要寫甚麼內容也可以問AI。

- `feat:` 新增功能
- `fix:` 修復 Bug
- `style:` 介面樣式調整
- `refactor:` 程式碼重構
- `chore:` 依賴更新或設定調整
- `doc:` 新增修改文件

### 💡 小提醒

#### 1. 頻繁 Commit

**觀念：** 「早點提交，經常提交 (Commit early, commit often)」。

- **進度存檔：** 就像打遊戲一樣，每過一小關就存檔一次。如果下一秒寫壞了，你可以輕易回到 10 分鐘前的狀態。
- **原子提交 (Atomic Commits)：** 每次 Commit 只做一件事。不要累積了一整天、改了五個檔案才 Commit 一次。

#### 2. 當你剛按下 Commit 才發現有錯字 (Amend)

**場景：** 剛按下提交，才發現少加一個圖檔或是註解寫錯。

- **專業作法：** 使用 `--amend`，這能讓你像是有「修正液」一樣。

```bash
git add .
git commit --amend --no-edit # 把現在的修正直接「塞進」上一個 Commit 紀錄
```

_這樣你的紀錄看起來會像是一次到位，沒有瑕疵。_

#### 3. 當你與同伴改到同一個檔案時 (Rebase)

**場景：** 你寫好了功能要推上去，卻發現同事已經先推了進度，導致衝突。

- **專業作法：** 使用 `git pull --rebase`。這會讓歷史紀錄看起來像是一條直線，而不是糾結在一起的毛線球。

```bash
git pull --rebase origin develop
```

_這會把你的改動「接」在同事的最新進度之後。_

### 🚩 檢查清單

1. **Docker 環境驗證**：在發起 PR 之前，必須確保改動在 Docker 啟動的 `http://127.0.0.1:5173` (前端) 與 `http://127.0.0.1:8000` (後端) 中運行無誤。
2. **上傳檔案管理 (uploads)**：

- **禁止 Commit 實體上傳檔**：`backend/uploads/` 下除了 `.gitkeep` 以外的任何檔案嚴禁進入 Git 紀錄。
- **測試附件**：若需測試檔案功能，請自行在本地放入測試檔，勿推送到 GitHub。

3. **API 與 Schema 一致性**：若修改了後端 `app/schemas/` 或 `app/models/`，前端必須同步更新對應的 API 請求邏輯。
4. **環境變數規範**：

- **嚴禁上傳 `.env**`：敏感的 `DATABASE_URL` 或密碼絕對不能 Commit。
- 本地 Docker 連線請統一使用 `db:3306`。

5. **推送前檢查**：

- 移除所有偵錯用的 `console.log` 與後端的 `print()` 紀錄。
- 確認代碼符合排版規範，且資料庫欄位註解（comment）已正確更新。
