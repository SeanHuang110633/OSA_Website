# ADR-002：後端架構與技術棧選型

**日期：** 2026-01-20

---

## 1. 背景

學務處系統正由舊有的 PHP 單體架構重構為現代化的前後端分離架構。後端系統面臨以下挑戰：

1. **多語系支持：** 系統需支援中英雙語，涉及複雜的資料回補（Fallback）邏輯。
2. **資料整併需求：** 未來需整併其他單位的異質資料。
3. **開發效率與品質：** 使用團隊成員熟悉的框架與套件，方便快速合作、理解且不易寫壞。

## 2. 決策

決定採用以下技術與架構模式：

- **核心框架：** FastAPI
- **資料庫：** MySQL
- **ORM 工具：** SQLModel (基於 SQLAlchemy 2.0 與 Pydantic 2.0)
- **架構模式：** 分層架構 (Layered Architecture)
- **Repository 層：** 處理原始資料存取（SQL 查詢、關聯預先載入）。
- **Service 層：** 處理核心業務邏輯與資料轉換（DTO Mapping）。
- **Router 層：** 處理 API 入口、請求驗證與路由分發。

- **依賴注入：** 使用 FastAPI `Depends` 機制進行解耦。

---

## 3. 理由與考量

### A. 關注點分離

- **Router 層的流量控制：**
  作為系統的門戶，Router 負責定義 API 合約（如路徑 `/events/{event_id}` 與方法 `GET`）。其核心職責包括：
- **參數驗證：** 利用 FastAPI 的 `Path` 與 `Query` 元件，在進入業務邏輯前即時攔截非法請求（例如：頁碼必須大於等於 1）。
- **依賴注入 (DI)：** 透過 `Depends` 注入所需的 Service，確保 Router 本身不需處理實例化邏輯。
- **回應格式化：** 使用 `response_model` 確保 API 回傳格式符合 DTO (Data Transfer Object) 規範，防止敏感資料外洩。

- **Service 層的邏輯封裝：**
  實現業務操作的統一管理。例如：針對多語系需求，在 Service 中實作降級策略（如找不到英文則自動回補繁中），確保 Router 層的程式碼簡潔且專注於通訊協定。
- **Repository 層的效能優化：**
  統一封裝資料庫操作，透過 `selectinload` 等技術解決 N+1 查詢問題，使業務邏輯層無需關注資料庫底層細節。

### B. 框架選型比較：為何選擇 FastAPI？

在評估 Python 後端生態系時，我們比較了主流的三種框架：

| 評估維度     | **Flask**                               | **Django**                                 | **FastAPI (本決策)**                            |
| ------------ | --------------------------------------- | ------------------------------------------ | ----------------------------------------------- |
| **開發速度** | 快，但缺乏結構規範，易寫出混亂代碼。    | 慢，由於「全功能組合」包袱較重，設定繁瑣。 | **極快，現代化語法與自動化工具支持。**          |
| **型別安全** | 弱，需額外外掛 Pydantic 等工具。        | 中，有自己的驗證機制但不夠現代化。         | **強，基於 Python Type Hints 實現自動驗證。**   |
| **效能**     | 一般，主要基於同步 (Synchronous) 設計。 | 較低，架構笨重且非同步支持較晚。           | **極高，基於非同步 (Asynchronous) ASGI 架構。** |
| **API 文件** | 需手動撰寫或整合第三方套件。            | 需安裝插件且自定義成本高。                 | **原生內建 Swagger (OpenAPI) 互動式文件。**     |

**選擇 FastAPI 的核心原因：**

1. **高性能非同步：** 系統未來涉及 RAG (LLM) 與爬蟲等高 I/O 任務，FastAPI 的 native async 支持能大幅提升併發處理能力。
2. **開發者體驗：** 強大的型別提示 (Type Hints) 配合 Pydantic，能讓編譯器或 IDE 捕捉 90% 以上的低級錯誤，降低團隊協作成本。
3. **自動化文件：** 啟動後即自動生成 `/docs` (Swagger) 介面，讓前端組員能即時查看 API 定義並進行 Mock 測試，解決前後端通訊不一致的問題。

### C. 型別安全與減少冗餘 (Type Safety & Efficiency)

- **SQLModel 的優勢：** 傳統開發需維護 DB 模型與 Pydantic 模型。使用 `SQLModel` 能讓一份 Class 定義同時具備兩者功能，大幅減少維護多份模型代碼的痛苦。

---

## 4. 影響

### 優點

- **代碼高度模組化：** 新加入的開發者只需關注對應的層級（例如：調整 API 格式改 Schema，改邏輯找 Service）。
- **穩定性提升：** 分層處理錯誤（如 Service 拋出 404，Router 接收並統一回應格式），系統行為可預測且穩定。
- **利於未來擴展：** 結構化的 Repository 與 Service 設計，讓未來整併異質資料或切換 RPC 框架時不需大改核心流程。

### 挑戰

- **開發初期的繁瑣：** 相比直接在單一檔案寫完所有邏輯，這種架構需要建立較多檔案（Model -> Repository -> Service -> Router），對簡單功能的開發速度略有影響。
