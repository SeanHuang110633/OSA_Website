# 後端開發架構指引

為了確保**OSA 系統 (學務處系統)**的長期穩定與易於維護，我們採用了目前 FastAPI 社群推薦的 **分層架構 (Layered Architecture)**。本文件將詳細說明此架構的設計原則與實作方式。

---

## 🏗️ 一、 為什麼選擇分層架構？

### 1. 分層架構的優缺點分析

| **特性**           | **優點 (Pros)**                                           | **缺點 (Cons)**                                                      |
| ------------------ | --------------------------------------------------------- | -------------------------------------------------------------------- |
| **職責分離 (SoC)** | 每個層級只關心自己的事。例如：資料庫改動不影響 API 定義。 | **程式碼量增加**：簡單的功能也需要寫多個檔案，初期開發稍慢。         |
| **可測試性**       | 邏輯被抽離，可針對單一 Service 進行測試，不需啟動資料庫。 | **開發門檻**：開發初期需要時間理解層級間的依賴關係。                 |
| **維護性**         | 邏輯集中在 Service 層，避免同樣的邏輯散落在多個 API 中。  | **效能損耗**：資料在層級間傳遞轉換會有微小的性能開銷（通常可忽略）。 |

### 2. 架構對比與適用情境

| **架構類型**              | **核心特點**                                | **適用情境**                                 |
| ------------------------- | ------------------------------------------- | -------------------------------------------- |
| **腳本式 (Scripting)**    | 邏輯全寫在 API 端點中。                     | 快速原型、個人小型工具。                     |
| **分層架構 (我們採用的)** | **Router → Service → Repository → Model**。 | **中大型企業應用、長期維護專案、多人協作。** |
| **整潔架構 (Clean Arch)** | 嚴格隔離核心業務與外部框架（更複雜）。      | 業務邏輯極度複雜且需頻繁更換底層技術的專案。 |

### 3. 為何 OSA 系統適用分層架構？

學務處系統具備以下特性，因此分層架構是我們的首選：

1. **長期維護需求**：校務系統通常運作多年，分層能確保未來更換資料庫或框架時，核心業務邏輯不被破壞。
2. **複雜業務規則**：例如**多語系降級邏輯**、**狀態管理（草稿/發布/封存）** 等，這類邏輯若寫在 API 層會導致程式碼難以閱讀。
3. **多人協作**：清晰的資料夾分工，可以減少多人在同一檔案同時修改產生的衝突（Conflict）。

## 📂 二、 專案目錄架構與功能說明

### 1. 架構圖概覽

Plaintext

```
WEBSITE_BACKEND/
├── app/
│   ├── core/           # 核心連線與環境設定
│   ├── models/         # 資料庫模型 (SQLModel/ORM)
│   ├── schemas/        # 資料傳輸物件 (Pydantic/DTO)
│   ├── repositories/   # 資料存取層 (CRUD & Query)
│   ├── services/       # 業務邏輯層 (大腦)
│   ├── routers/        # API 路由層 (入口)
|   ├── dependencies.py # 統一處理依賴注入的工廠函式
│   └── main.py         # 應用程式進入點
```

---

### 2. 各層級深入解析 (以 Event 功能為例)

#### **A. 核心設定層 (`app/core/`)**

負責資料庫引擎（Engine）的建立與會話（Session）管理。

- **功能**：設定 `DATABASE_URL` 並處理連線回收，防止連線斷掉。
- **範例**：`database.py` 提供 `get_session` 依賴項，供後續層級呼叫。

#### **B. 資料模型層 (`app/models/`)**

定義資料庫表格的結構 (Schema)。

- **功能**：對應 MySQL 實體表格，定義欄位屬性與關聯（Relationship）。
- **Event 實例**：`Event` 模型定義了 `category_id` 外鍵，並連結 `translations` (翻譯) 與 `attachments` (附件)。

#### **C. 資料傳輸物件 (`app/schemas/`)**

定義 API 輸入與輸出的 JSON 格式。

- **功能**：確保不直接暴露資料庫敏感欄位（如 `deleted_at`），僅提供前端所需的資料，且支援資料型態驗證。
- **Event 實例**：`EventListView` 負責列表顯示，`EventDetailView` 則包含更詳盡的 `content` 與 `attachments`。

#### **D. 資料存取層 (`app/repositories/`)**

專門與資料庫溝通，不包含業務邏輯。

- **功能**：封裝 SQL 查詢(使用ORM框架，我們採用SQLModel)，此處理 **軟刪除過濾**、**狀態檢查** 與 **效能優化 (selectinload)**。
- **Event 實例**：`EventRepository.get_list()` 會自動過濾已刪除或未發布的活動，並預先載入分類資料。

#### **E. 業務邏輯層 (`app/services/`)**

系統的「大腦」，負責複雜的邏輯運算。

- **功能**：呼叫 Repository 拿資料(包含許多不需要的欄位)，並進行轉換(拿掉前端不需要及不應該出現的欄位)、多語系處理或權限判斷。
- **Event 實例**：`EventService` 負責判斷當前語言。如果 `en-US` 沒翻譯，它會自動「降級」尋找 `zh-TW` 版本回傳給前端。

#### **F. 路由層 (`app/routers/`)**

API 的進入點，負責接收請求並回傳結果。

- **功能**：定義網址（URL）、HTTP 方法（GET/POST）以及輸入參數驗證。
- **Event 實例**：`event_router.py` 透過 `Depends(get_event_service)` 注入evebt_service.py中寫好的服務，並回傳轉換好的 `EventListView`給前端。

## 🛠️ 三、 開發標準流程 (Workflow)

當你需要新增一個功能（例如：下載區 `downloads`）時，請遵循以下順序：

1. **Models**: 在 `models/` 定義表格與關聯(就是把資料庫中的table結構映射過來)。
2. **Schemas**: 在 `schemas/` 定義 API 輸出入格式(就是前、後端交互的資料格式)。
3. **Repository**: 在 `repositories/` 寫入 SQL 查詢邏輯（使用ORM框架不直接寫純SQL）。
4. **Service**: 在 `services/` 處理主要業務邏輯(包含多語系轉換、資料組裝成定義好的schema等等)。
5. **Router**: 在 `routers/` 開發 API Endpoint 並注入 Service。
